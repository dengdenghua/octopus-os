# Echo OS 首次使用与支持指南

本指南面向首次配置 Echo OS 的设备管理员和处理用户问题的支持人员。目标是在不跳过权限边界、
不代用户发送任务、也不要求用户执行危险存储命令的前提下，完成第一个可验证任务并收集足够的
脱敏诊断信息。

## 十分钟首次使用流程

登录桌面后，首次使用卡片提供四个入口。旧版引导已经关闭的账号可在“系统设置 → 通用与更新 →
首次使用与支持”重新打开。引导按账号保存；有已完成任务的老账号不会被自动打断。

### 1. 数据目录与共享

打开“共享与用户”，确认至少有一个状态可用、用途明确的受管共享目录。创建或修改共享时：

- 只使用界面提供的候选卷和目录，不手工输入宿主绝对路径；
- 在应用前阅读 plan 预览，确认目标、协议、读写方式和影响范围；
- 需要写入时由设备管理员完成一次性审批；
- 创建后刷新页面，确认共享、SMB/NFS 状态及权限来自实际回读，而不是只看到“请求成功”；
- 不确定数据盘是否可清空时停止操作，不尝试格式化、建池或换盘。

家庭成员只能访问当前 ACL/组权限允许的数据。需要新增或修改成员权限时，由管理员在同一页面
预览并审批；不要通过 Everyone、guest、宽泛 CIDR 或放宽父目录权限来绕过失败。

### 2. 模型与连接

打开“模型与用量”，确认页面显示当前系统默认模型及连接状态。选择模型前先判断数据边界：

- 云模型会把当前任务所需内容发送给对应提供方；
- 本地模型不可用时应明确等待或报错，不会静默改用云模型；
- 系统默认只影响后续发送，已经开始的任务继续使用其已提交快照；
- 不在聊天、截图、诊断包或工单中粘贴 API key、恢复码或管理员密码。

连接状态仍在检查或显示错误时，先处理连接，不要把“任务未发送”误判为 Agent 故障。

### 3. 执行与安全权限

打开“AI 与 Agent → 执行与安全”，核对审批规则和沙箱范围。首次使用建议：

- 保持“未匹配规则时询问审批”或更严格策略；
- 只对明确工具和必要参数范围放行，不使用宽泛通配符长期允许写操作；
- 文件、浏览器、桌面和系统操作分别授权，不因一个能力已允许而推定其他能力也已允许；
- 删除、覆盖、外发、安装、账户、共享和存储变更应继续要求明确确认；
- 任务中途撤权后重新执行必须按当前权限判断，不能依赖旧回执绕过。

### 4. 完成第一个任务

“在 Agent 工作台准备示例任务”只把下面的安全样例填入输入框，不会自动发送：

> 请为我写一份简洁的每周工作计划模板，包含目标、任务、时间安排和复盘。先在对话中展示结果，
> 不修改本地文件。

发送前由用户确认模型、权限和文字内容。任务完成后，在“任务空间”确认状态为完成，并打开结果；
如果产生文件，再从“本地数据库”定位同一资源。只有界面结果、任务记录和实际资源互相一致，才算
完成首次任务。

## 常见问题定位

| 现象                          | 先检查                                               | 安全处理                                            |
| ----------------------------- | ---------------------------------------------------- | --------------------------------------------------- |
| 登录后反复回到登录页          | 设备时间、账号状态、Cookie/Bearer 是否已被管理员撤销 | 重新登录；不要复用旧令牌或关闭认证                  |
| 模型一直检查中或不可用        | “模型与用量”的连接状态和提供方范围                   | 修复对应连接；本地模型缺失时等待下载或明确切换      |
| 任务没有开始                  | 输入框是否仍有草稿、是否点击发送、是否等待审批       | 阅读审批内容后决定；不要通过修改数据库伪造完成      |
| 任务等待或中断                | “任务空间”的等待原因、审批、接管与恢复入口           | 使用原任务的恢复入口；未知副作用时不要重复执行      |
| 看不到文件或照片              | 当前账号的共享/相册权限和原件是否仍存在              | 由管理员修正当前权限；不要复制父目录绕过子项限制    |
| SMB/NFS 访问被拒绝            | 用户/组、共享权限、客户端身份和协议启用状态          | 用目标账号重新验证；不要开启 guest 或扩大到任意网络 |
| 存储健康显示 unknown/degraded | 告警代码、探针状态、工具/权限是否可用                | 先保持数据只读和备份；不要把探测失败当作健康        |
| 更新无法应用                  | 更新签名、目标版本、当前任务及维护状态               | 保留当前版本，按页面给出的恢复动作处理              |

## 导出支持诊断包

设备管理员可在“系统设置 → 通用与更新 → 支持诊断包”主动导出 ZIP。成功导出会写入防篡改
审计链，浏览器显示实际下载文件名。

诊断包只包含固定白名单摘要：

- 平台、架构、内核、Python 与 Echo 版本；
- 十二个 NAS 必需命令是否可用；
- 存储健康状态、资源数量、告警严重度/代码和探针状态的聚合计数；
- 审计链完整性和签名密钥数量；
- 每个载荷的大小及 SHA-256 manifest。

诊断包明确不包含：

- 原始日志、原始命令输出或任意配置文件；
- 账号、密码、令牌、密钥、恢复码或环境变量；
- 主机名、IP、网络端点或远端 URL；
- 挂载路径、文件名、目录内容、磁盘序列号或设备身份。

归档硬上限为 512 KiB。支持人员若需要额外信息，应逐项说明用途并让用户主动提供；不能要求用户
上传整个状态目录、认证目录、备份凭据、审计正文或磁盘镜像。

## 支持工单最小信息

建议只收集：

1. 问题发生时间与用户看到的固定错误码；
2. 操作入口和最后一个明确确认的步骤；
3. 是否可稳定复现，重试是否可能重复副作用；
4. Echo OS 版本、安装形态和硬件架构；
5. 用户主动导出的诊断包；
6. 是否涉及数据不可读、权限异常、断盘、断电或更新失败。

不要让用户在公开工单粘贴管理员密码、TOTP 秘钥、恢复码、Cookie、Authorization header、完整
Webhook URL、SMTP 账号/应用密码/完整收件地址、云模型 API key、备份仓库密码或未经脱敏的配置。

## 必须停止并升级处理的情况

出现下列任一情况时停止写操作，保护现场并升级给具备设备和恢复权限的负责人：

- 数据摘要变化、文件意外消失或权限边界被绕过；
- 阵列多成员故障、池状态不明、设备身份无法稳定确认；
- 更新、恢复或换盘结果未知，重复执行可能扩大影响；
- 断电后无法确认文件系统、审计链或任务回执完整；
- 需要使用 `--force`、直接编辑阵列/池元数据、清除签名或删除非空目录才能继续。

Echo OS 当前不把 Btrfs balance/任意设备增删、多故障恢复、ZFS 任意布局/强制导入、复杂递归 ACL、
非空共享删除或未经验证的自动修复伪装成受支持能力。此类需求应先备份并在隔离介质验证，不应由
一线支持临场执行。

## 发布边界

本指南和本机回归不能替代冻结候选的 x86/ARM 实机、跨 Windows/macOS/Linux 的 SMB/NFS、真实
Time Machine、UPS、硬断电、签名更新/回滚及裸机恢复验收。正式发布结论以
[NAS 交付状态](../NAS_DELIVERY_STATUS.md)和
[实体设备检查清单](../P1_P2_REAL_DEVICE_CHECKLIST.md)为准。
