## 1. 目标与假设

定位：面向个人设备与私有数据的 Agent 操作系统。

首批用户建议聚焦有 NAS/迷你主机、愿意参与测试的个人与小团队。核心价值是让用户用自然语言完成有明确结果的文件、应用和设备任务，并能查看、批准、停止和恢复执行。

本轮目标：形成一个可重复安装、可完成三类真实任务、失败可解释且恢复可验证的受限测试版本。完整 NAS 替代、通用桌面替代与算力集群操作系统不作为本轮验收目标。

排期假设：2–3 名开发者，具备 Linux 构建环境、一台 x86_64 参考机、可清空测试盘和独立备份介质，约 8–10 周。若只有一名维护者，保留阶段顺序并缩减场景数量，不通过减少恢复测试压缩工期。此为预算安排，不是交付承诺。

本方案基于当前文档和部分代码检查，未重新执行整套测试或真机验收。已有测试数字不作为本轮实测基线。所有数值目标均为建议验收门槛，需在阶段 A 测量后冻结；调整必须记录原因。

## 3. 三条产品任务

### 场景一：文档整理与检索（首先交付）

用户目标：“把这个目录里的发票按年月整理，列出不能确定的文件，并找到某笔支出的原件。”

闭环：选择授权目录 → 只读扫描 → 提取与分类 → 预览变更清单 → 按现有策略确认 → 执行 → 回读结果 → 提供原件链接和撤销入口。

验收：同名不覆盖；无法识别进入待确认；输出分类与原文件逐一可追溯；每个文件结果通过独立清单验证。再次运行不得重复移动。撤销只恢复本次操作且目标未被外部修改的对象；冲突须报告，不能覆盖后续修改。

依赖：文件能力、索引/提取服务、任务投影。索引服务不可用时允许文件名检索或手工规则整理，语义检索明确不可用。首版仅支持明确列出的文件格式。

### 场景二：下载后媒体整理

用户目标：“将下载完成的视频整理到媒体目录，再让媒体库识别。”

闭环：确认下载完成 → 排除临时文件 → 生成命名与移动计划 → 处理冲突 → 执行 → 调用媒体服务刷新 → 验证索引结果。

验收：不处理下载中的文件；低置信度匹配需要确认；重复事件不产生重复副作用；媒体刷新失败时保留文件整理的真实成功状态，只重试刷新步骤。第三方服务不可达不得将整项任务伪报完成。

依赖：文件任务已稳定、一个固定版本的媒体服务、受限连接凭据。首版只支持一个下载来源与一个媒体服务；连接器缺失时先做窄 API 适配，不通过任意 shell 实现通用集成。

### 场景三：备份异常诊断与恢复

用户目标：“备份为什么没完成？修复后继续。”

闭环：读取状态 → 区分断网、目标盘掉线、空间不足和权限错误 → 展示原因与建议 → 用户处理硬件或批准支持的修复 → 恢复传输 → 哈希校验。

验收：用受控故障分别触发上述四类问题；缺少目标挂载时不得写入同名宿主目录；恢复后内容一致；不可恢复任务给出下一步和原始数据保留位置。

首版建议选择已具备续传机制的文件备份路径。设备状态备份与用户数据备份必须分开说明，不能将前者显示为“全部数据已备份”。Android 实体机自动备份在对应真机验收完成前标记为实验能力。

## 6. 技术优化约束

### 权威状态与任务模型

继续由 Agent TaskSupervisor 管理通用任务生命周期，OS 投影其状态；ProjectOS 已有任务 claim，cowork、文件、相册和应用保留各自领域的执行与资源状态权威，通过关联 ID 对齐，不强行替换成一个新队列。投影层不能从聊天措辞或进度动画推断完成。

### 权限与隐私

保留现有单次审批，不因追求少点击而默认放开系统控制。减少无效重复提示应优先改进计划聚合和展示；若未来扩展批量授权，必须限定精确目标、动作、有效期与变更集合。

针对外部文档/网页内容诱导删除、外传、执行命令的样本，验证 provider 硬权限和审批边界。文本定界或模型自我约束不能作为通过依据。

文件“存储在本地”不代表模型调用不会外传。首次使用显示推理提供方和内容发送范围；本地模式不可用时明确等待或失败，不静默改用远程模型。实现前核对现有路由政策。

### 资源与性能

先测空闲、单任务、后台索引三种状态，记录参考机 CPU、内存、磁盘、模型位置、数据规模和冷/热缓存。随后按热点优化，避免整套运行时重写。

优先检查可选模块惰性加载、目录分页/增量扫描、索引并发限流、前端大列表渲染和事件订阅清理。缓存必须按用户/权限隔离；权限改变后不能继续返回过期授权内容。

模型不可达时文件管理和已有确定性操作应继续可用。模型服务、索引服务与桌面基本操作分别报告健康状态。

## 7. 指标与测量方法

以下为建议目标，非当前成绩。测量时固定模型版本/配置、OS revision、参考硬件和输入样本；失败、超时与缺失运行不得从分母中移除。

| 指标           | 定义与样本                                                                   | 建议门槛                                                        |
| -------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 正常任务成功率 | 每类 20 个固定正常用例，每例 3 次；独立验证最终文件/服务状态，按场景分别报告 | 每类至少 54/60 成功；用于内部准入，不推断生产 SLA               |
| 人工纠偏       | 除预定审批外，需要补充指令或手工修正的正常任务占比                           | 每类不高于 20%；同时报告全部失败                                |
| 权限与安全样本 | 越目录、跨用户、审批重放、计划篡改、注入诱导等固定用例                       | 所列用例全部拒绝或停在有效授权边界；不代表穷尽所有攻击          |
| 故障恢复       | 可恢复的进程中断、断网、容量不足等用例，每例 3 次                            | 全部保持内容一致且不重复副作用；不支持的恢复明确报告            |
| 数据完整性     | 测试盘上记录操作前后内容哈希及预期变更清单                                   | 无非预期修改或丢失；任一失败阻断晋级                            |
| 任务反馈       | 从提交到看到已接受/排队状态，参考局域网下 100 次                             | p95 ≤ 1 秒，不包括模型完成时间                                  |
| 资源回收       | 暖机后完成 50 次串行任务，静置后比较进程树 RSS                               | 相对暖机基线增长 ≤ 10%；超过则分析缓存/泄漏再决定               |
| 运行稳定性     | 先满足现有 24 小时门，再做 72 小时混合负载 soak                              | 无未恢复服务故障、数据异常或无限资源增长                        |
| 模型成本与耗时 | 每个成功任务及每次尝试的 token、实际报告费用、耗时中位数/p95                 | 阶段 A 后冻结预算；缺失费用写未知，禁止填 0；优化不得牺牲通过率 |
| 首次使用       | 5–10 名试用者在预装参考设备上，从打开引导到完成首个简单任务                  | 至少 80% 在 10 分钟内完成；记录模型下载耗时，不混入隐藏准备工作 |

必要审批次数单独统计，不计入人工纠偏。性能数字必须附测量条件，不作为未测试硬件的承诺。
