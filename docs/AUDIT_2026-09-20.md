## 二、P0 详解

### P0-1 · 分支无 upstream，CI 从未运行

```
$ git remote -v
upstream  https://github.com/dengdenghua/octopus-os.git (fetch)
upstream  https://github.com/dengdenghua/octopus-os.git (push)

$ git rev-parse --abbrev-ref 'p3-provision@{upstream}'
fatal: no upstream configured for branch 'p3-provision'
```

- 仓库只有**一个** remote：`upstream`（上游公开仓库），没有个人 fork。
- `os-main` 的 tracking 显示为 `[upstream/os-main: gone]`。
- 触发条件已修好：`ci.yml:5-8` 的 `branches` 现在包含 `p3-provision`（这是上一轮 P0 的修复成果，已确认生效）。
- 但**没有 upstream 就没有 push 触发**，10 个 job（`workflow-contract` / `untracked-source-guard` / `public-source-contract` / `frontend` / `lint-and-test` / `pytest-cross-platform` / `full-test-suite` / `security-scan` / `omv-host-bundle` / `docker-build`）一次都没执行过。

→ 需要拍板：推到哪个远端？（直推 `upstream` 的公开仓库 vs 先建 fork）

### P0-2 · 13 个未跟踪源码文件

```
$ python tools/lint/untracked_source_check.py
FAIL · 13 untracked source file(s) — they are invisible to CI and to every fresh clone:
  frontend/src/appliance/agent-pip-monitor.tsx        (+ .test.tsx)
  frontend/src/appliance/ai-network-pulse.tsx         (+ .test.tsx)
  frontend/src/appliance/intent-desktop-surface.tsx   (+ .test.tsx)
  runtime/execution/all_skills/crash-triage/SKILL.md
  runtime/execution/all_skills/crash-triage/scripts/triage.py
  runtime/platform/observability/crash_reporter.py
  runtime/sensing/gateway/_observability_crashes.py
  tests/test_crash_endpoints.py
  tests/test_crash_reporter.py
  tests/test_doctor_crashes.py
exit=1
```

契约测试同步失败：

```
$ pytest tests/test_ci_gate_contract.py -q
FAILED tests/test_ci_gate_contract.py::test_no_untracked_source_files
1 failed, 12 passed in 1.98s
```

**风险实质**：整个「崩溃 AI 诊断」能力（crash_reporter → /api/crashes 端点 → crash-triage skill → doctor 检查）**只存在于本地工作区**，没有进 git。一次误操作或磁盘故障就全没了。

### P0-3 · 安全扫描被 12 条误报卡死

```
$ bandit -r appliance/ -ll -ii
>> Issue: 12 条（Medium）；bandit exit=1
```

逐条读源码后的判定——**12/12 全是误报**：

| 规则 | 数量 | 位置 | 为何是误报 |
|---|---|---|---|
| B608 SQL 注入 | 7 | `appliance/photos/service.py:751,876,882,888,894,941`、`appliance/sync.py:703` | `placeholders = ",".join("?" for _ in batch)` 生成的**只有问号占位符**，真实值走 `tuple(batch)` 绑定参数。bandit 看不见 placeholders 的生成方式 |
| B104 绑定全部网卡 | 2 | `appliance/lan_discovery_proxy.py:150`、`appliance/native_hub_firewall.py:95` | 都不是 socket bind：前者是 `if hostname not in {None, "", "0.0.0.0", "::"}` 的**校验比较**，后者是 Docker 端口绑定的**期望字典**用于比对 |
| B103 过度宽松权限 | 3 | `appliance/native_btrfs.py:492`、`appliance/native_ext4.py:455`、`appliance/native_storage.py:1764` | 前两处是 `root:root` 挂载点 `0o755`（`native_storage.py:1764` 的 `0o2770` 是 setgid+770，**比 755 更严格**，bandit 误判了 setgid 位） |

CI 里 `security-scan` 没有 `continue-on-error`，也没有 bandit 基线文件（`pyproject` 与 `ci.yml` 中均无 bandit 配置）。→ 必须加 `#nosec` 或基线，否则这门禁永远红、也就永远没人看。

## 三、P1 详解

### P1-2 · 默认测试入口只覆盖 14%

```toml
# pyproject.toml:272-280
[tool.pytest.ini_options]
testpaths = ["tests/appliance"]
```

| 入口 | 收集数 |
|---|---|
| `pytest`（默认，亦即 `make test` / `make test-fast`） | **2394** |
| `pytest tests/`（仅 `full-test-suite` job 使用） | **约 16776** |

`tests/` 顶层有 **1066** 个 `test_*.py`，`tests/appliance/` 只有 **181** 个。也就是说开发者本地随手跑一次 pytest，看到的绿灯**与另外 86% 的用例无关**。
`full-test-suite` job 是为补这个洞加的，但目前 `continue-on-error: true`（观察期），且**从未真正跑过**（见 P0-1）。

### P1-3 · 本地 venv editable 安装指向陈旧目录

```
$ cat .venv/Lib/site-packages/_editable_impl_echo_os.pth
C:\飞牛os\octopus-os        ← 5 行重复
$ ls C:\飞牛os\octopus-os\deploy
ls: cannot access ...: No such file or directory
```

当前工作区是 `D:\飞牛os\echo-os`，但 editable 装的是 `C:\飞牛os\octopus-os`。后果：任何**在非仓库根 cwd 起 Python 子进程**的用例都会 `ModuleNotFoundError: No module named 'deploy'`。

这直接制造了 3 条假失败：

```
FAILED tests/appliance/test_operations_bundle.py::test_bundled_storage_provisioning_lab_runs_with_sibling_dependencies
FAILED tests/appliance/test_operations_bundle.py::test_bundled_btrfs_provisioning_lab_has_sibling_dependencies_and_runs_standalone
FAILED tests/appliance/test_operations_bundle.py::test_bundled_mdraid_replacement_lab_runs_with_sibling_dependencies
```

**实证定性**（不是推测）：临时把正确路径写进 `.pth` 后——

```
$ python -E -c "import deploy.appliance.external_storage"
OK deploy 可导入: D:\飞牛os\echo-os\deploy\appliance\external_storage.py

$ pytest tests/appliance/test_operations_bundle.py -q
12 passed in 4.30s
```

验证完已把临时 `.pth` 删除，环境恢复原状。修复动作是重跑一次 `uv sync`（或 `pip install -e .`）。

> 注：`pyproject.toml:244` 的 wheel `packages` 只含 `appliance/runtime/tools/echo_runtime/demos`，`deploy/` 靠 `force-include` 只进了 4 个文件（`external_storage.py`、`nas_data_backup*.py`）。因此 CI 上 `deploy` 能否导入**完全依赖 editable 安装**——这也是为什么该修 venv 而不是改测试。
