# 相册模型加载与本机实测

日期：2026-09-07。本文区分依赖安装、模型加载、检索结果和发行验证。

## 当前模型与配置

当前图像/文字编码器分别为 `Qdrant/clip-ViT-B-32-vision` 和
`Qdrant/clip-ViT-B-32-text`，向量为 512 维。锁定的 FastEmbed 0.8.0 模型描述将文字
模型标为 English、77 token 上限；模型可运行不代表中文检索效果达标。

| 配置 | 当前行为 |
| --- | --- |
| `ECHO_IMAGE_SEMANTIC=0` | 关闭智能索引和语义检索；浏览、预览及文件名检索继续按各自能力工作 |
| `FASTEMBED_CACHE_PATH` | 显式指定 CLIP 缓存；未设置时本轮改为 `app_paths().data_dir/models/images`，原来默认使用系统临时缓存 |
| `HF_HUB_OFFLINE=1` | CLIP 只读取本地缓存；缓存缺失时报加载失败，不转用远程推理 |
| `ECHO_ORT_PROVIDERS` | 默认 CPU；显式指定的 provider 必须在实际 ONNX Runtime 中可用，不能把配置字符串当作 GPU 生效证据 |
| `ECHO_EMBED_QUANTIZE` | 空值或 `float32` 使用默认模型；`int8/uint8` 当前明确拒绝。锁定 FastEmbed CLIP 实现不处理该量化参数，原来透传它不能产生所声称的量化效果 |
| `ECHO_IMAGE_MAX_CONCURRENT_INFERENCE` | 本地图片/视频 CLIP 与人脸原生推理的并发上限，默认 1，最多 4；只限制模型调用，不限制文件扫描或 SQLite 读写 |
| `ECHO_IMAGE_INFERENCE_WAIT_SECONDS` | 推理准入等待上限，默认 2 秒，最多 30 秒；超时返回 `image_inference_busy` 并保留上一次索引快照 |
| `ECHO_IMAGE_EMBED_BATCH_SIZE` | 相册重建一次送入 CLIP 的图片数，默认 8，限制在 1–64；批量失败会逐图重试以保持单图失败隔离，内存紧张时可设为 1 |
| `ECHO_IMAGE_INFERENCE_GATE_DIR` | 可选的同一设备跨进程推理闸门目录；未设置时使用 `app_paths().data_dir/image-inference-gate`，目录不可用则安全退回进程内限制 |

缓存默认值变更不会自动搬迁旧缓存；已有完整缓存可用 `FASTEMBED_CACHE_PATH` 继续
指定。人脸模块仍使用其原有模型加载路径，本轮没有将 CLIP 离线开关推广为所有视觉
模块的统一离线保证。

参考：[Qdrant 本地缓存与离线加载](https://qdrant.tech/documentation/edge/edge-fastembed-embeddings/)、
[FastEmbed 模型及接口](https://github.com/qdrant/fastembed)。实现与接口验证以仓库
`uv.lock` 的 0.8.0 实际代码为准。

## 状态与错误

状态查询只检查依赖是否可发现和内存中的加载记录，不导入推理库、不加载或下载模型。
`available` 表示依赖与接口允许尝试；`modelsLoaded` 才表示当前进程已加载。
界面区分 `dependencies-ready`、`loading`、`load-failed` 与 `loaded`，失败后保留
明确的索引重试入口和原审批流程。查询触发首次文字模型加载后，也会刷新状态。

加载错误只发布固定 code：运行库导入失败、不支持的量化、无效配置、其他模型加载
失败。原始异常可能包含本地路径、下载 URL 或凭据，不进入照片 API 或界面。

## 真实运行结果与限制

使用本机 `.venv`，从 `uv.lock` 导出约束后安装 FastEmbed 0.8.0、ONNX Runtime
1.29.0 及对应依赖；没有修改锁文件。已有 NumPy 2.5.2、Pillow 12.3.0。

初次尝试在 Windows 11 build 26100、Ryzen 7 8745H 上发生真实 ORT DLL 初始化失败。
系统 `msvcp140.dll` 为 14.36.32532；仅在测试子进程显式加载已有工具运行时中的
14.51.36247 后，同一 ORT 包可以导入。没有修改系统 DLL，也没有把工具运行时路径
写入产品。官方要求 Windows 配备 Visual C++ 运行库，见
[ONNX Runtime 安装说明](https://onnxruntime.ai/docs/install/)。正式 Windows 交付
仍需按官方运行库安装路径验证，不能依赖本次诊断用的临时加载方式。

首次实际下载并索引三个合成形状用时约 281 秒，首次文字查询约 115 秒，包含下载和

## 内容身份

本轮新增 `image_fingerprints`，对已安全解码的图片按条带计算 SHA-256，包含模式、
尺寸、像素与 EXIF。它是派生缓存身份，不是原始照片文件校验和。
同 mtime/尺寸但像素变化时，旧 OCR、标签和保留的人脸结果会失效；新旧指纹和其他
索引同事务提交，失败则保留原快照。没有指纹的旧派生缓存首次重建会保守失效。

后续增量构建同时核对内容指纹和编码器身份。已知 FastEmbed 模型在加载后记录模型
资产、预处理配置、相关包版本及实际 provider 的 SHA-256 身份，绑定当前内存会话；
新进程会重新计算身份。仅有模型名称或向量维数不够，旧索引及未知 provider 全部重算。
人脸也按检测模型与源图身份复用，单独记录零人脸的完成结果，避免把未运行检测当成
没有人脸。模型权重更换、依赖版本变化、损坏向量都不能误用旧缓存。

人物命名及训练类别的原型也分别绑定编码器身份。已知模型不兼容时，旧名称和原型
保留在数据库，但不继续参与匹配；重新命名或训练可以建立新绑定。类别检查使用
当前已加载的图像模型身份，未重建索引时同样生效。人物及原型从同一读取事务取得，
命名则在同一写事务读分组并保存绑定。旧未知来源仅保留既有兼容行为，不把它当成
可验证的跨模型兼容性；完整重新确认界面尚待补齐。

## 增量、取消与恢复实测

沿用上述实际 CPU CLIP 和诊断 MSVC 条件，在独立合成图库中拦截网络、包装真实
`embed` 计数，并逐次核对 SQLite 结果。本表计时在模型加载完成之后开始，不能与
前文包含初始化的冷启动耗时直接比较。

| 变化 | 本次真实编码次数 | 复用数量 | 构建耗时 |
| --- | --- | --- | --- |
| 初始三张 | 3 | 0 | 0.219 秒 |
| 三张不变 | 0 | 3 | 0.015 秒 |
| 新增一张 | 1 | 3 | 0.047 秒 |
| 同 mtime/尺寸替换一张 | 1 | 3 | 0.047 秒 |
| 删除一张 | 0 | 3 | 0.015 秒 |
| 新进程、同模型和三张图片 | 0 | 3 | 0.016 秒 |

真实编码返回后请求取消，十二张持久表与取消前逐行一致，没有写入新任务回执。
两次进程都为 0 次网络尝试；证据见
[增量结果](C:/飞牛os/octopus-os/tmp/real-photo-incremental-m0yl6f6n/result.json) 和
[新进程结果](C:/飞牛os/octopus-os/tmp/real-photo-incremental-m0yl6f6n/fresh-process-result.json)。

相册取消接口校验管理权限与精确任务 ID，`running → cancelling → cancelled`；
不能中断的原生推理返回后才检查取消，因此停止请求不代表已立即停止。成功提交优先
于晚到的取消。相册只保存当前提交对应的回执，后续通用重建也会使旧回执失效。
独立固定向量进程试验使用真实 service、文件适配器和 SQLite：提交前被终止保留旧库
并报告中断；提交后、任务 JSON 更新前被终止，重启读取精确回执恢复成功，未加载
模型或重新构建。见 [中断结果](C:/飞牛os/octopus-os/tmp/photo-lifecycle-review-20260905/results.json)。

相册索引还支持安全暂停：`running → pausing → paused` 会在检查点回滚当前临时事务，
保留上一份已提交快照并释放写锁、模型准入和进程任务租约；`resume` 会重新校验原计划
和图库指纹，再以同一个任务身份重建。暂停状态写入任务日志，服务重启后仍可恢复或取消，
不会把“线程还活着”误报成可继续的索引。

这证明增量编码与原子快照恢复的行为，仍不是增量目录扫描、逐图片续算或大库性能
验收；人脸缓存控制流有固定模型测试，实际 InsightFace 推理和准确率尚未验证。

重建现在会把未命中缓存的图片按 `ECHO_IMAGE_EMBED_BATCH_SIZE` 分批送入一次 CLIP
调用，默认最多同时保留 8 张已解码图片，单批失败会退回逐图调用并继续隔离失败项。
缓存命中图片不会进入模型批次；因此增量重建不会因为批量优化重新编码未变化的照片。
这项改动降低了大库扫描的 Python/ONNX 调用次数，但没有把它写成吞吐承诺，实际内存
峰值仍需在目标 Linux/物理设备上测量。

## 推理资源闸门

设备相册的索引任务已经由相册服务限制为单任务并持有跨进程锁；通用 Agent 图片技能和
视频技能还可以直接调用同一组 CLIP/InsightFace 单例。现在这些入口共用
`image_semantic_index.inference_slot`：默认只允许一个原生模型调用，等待使用短间隔退避，
等待中的索引看到取消或暂停会立即退出；槽位只包住原生 `embed`/`get` 调用，返回后马上释放，
不会把 SQLite 事务或图片解码一起占住。默认闸门使用数据目录下的 OS 锁文件，因此同一设备
上不同服务进程会共享同一组槽位；`inference.processShared` 明确报告该目录是否可用。准入状态
通过 readiness 的 `inference` 字段提供 `maxConcurrent`、`active`、`waiting`、`available`
和 `processShared`；其中 `active`、`waiting`、`available` 是当前进程的观察值，跨进程争用
以实际准入结果为准，不包含线程、模型路径或异常正文。

准入超时不会覆盖旧索引，后台构建返回固定的 `image_inference_busy` 和
`resource_limited=true`，调用方可以在资源空闲后重新提交。该机制证明了单进程内的并发
等待中的索引收到暂停也会立即退出为 `paused`，上限、退避、取消释放和相册暂停后的重新排队
已在本地服务链路覆盖，且同一设备跨进程的 Windows 锁路径已有独立子进程回归；跨主机显卡
调度、内存峰值和长时吞吐仍需在目标 Linux/物理机上测量，不能由本地单元测试代替。
