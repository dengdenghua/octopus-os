# P0 / P1 / P2 / P3 Stack — operator handbook

This document summarises the safety / evolution / durability stack
that landed across the P-series workstreams. It's the operator's
single-page reference: what each layer does, where the knobs live,
and how to verify the whole thing is wired correctly before flipping
on production.

---

## 1. P2 — guard layer (37 ReAct guards)

The base layer. 37 guards that intercept the ReAct loop's
``Final Answer`` candidates and refuse them when they look like the
agent is virtual-shipping bad code. Categories:

* **Security** (5) — secret leak, destructive call, dynamic exec,
  shell injection, unsafe deserialization
* **Verification** (5) — language-mismatch, signature-typecheck,
  test-coverage, wire-schema, dependency-declaration
* **Test quality** (8) — weak assertion, mock-only, undocumented skip,
  deleted test, generic test name, no-assertion, false-verification,
  test path mismatch
* **Code-smell** (15) — print-in-prod, hardcoded path, sleep-in-prod,
  oversized edit, full-file rewrite, long-function, comment-out fix,
  broad-except, exception-swallow, frontend-tsconfig, async-without-
  await, network-in-loop, repeated-literal, magic-number, plus a
  catch-all completion guard
* **Protocol** (4) — inspection evidence, tool availability, tool
  result, todo protocol

Each guard is a ``GuardSpec`` in ``GUARD_REGISTRY``. They evaluate in
priority order via ``evaluate_guards``; the first hit wins.

**Source code:** [runtime/core/cerebrum/react_guards.py](../runtime/core/cerebrum/react_guards.py)

## 2. P1 — evolution loop

Closes the feedback loop on guard hits so the agent gets better
over time without a human in the loop:

```
ReAct turn → guard hit → guard_hits.jsonl
                              ↓
                       judge batch cron
                              ↓
                  digest (per-label precision)
                              ↓
              ┌───────────────┴───────────────┐
              ↓                               ↓
   prompt_evolver                        trust_signal
   (mutates prompt suffix)              (drives gate + evolver)
```

### Components

| Layer | What | Where |
|---|---|---|
| Telemetry sink | append-only jsonl | `runtime/safety/evolution/guard_telemetry.py` |
| Judge | LLM second-pass review | `runtime/safety/evolution/guard_judge.py` |
| Batch runner | nightly cron | `runtime/safety/evolution/guard_judge_batch.py` |
| Batch CLI | `python -m runtime.safety.evolution.run_batch_cron` | `runtime/safety/evolution/run_batch_cron.py` |
| Weekly report | Markdown digest | `runtime/safety/evolution/weekly_report.py` |
| Prompt evolver | trust-aware mutation gate | `runtime/safety/camouflage/prompt_evolver.py` |

### Cron

```cron
# Nightly: drain unjudged hits
0 3 * * * python -m runtime.safety.evolution.run_batch_cron --max-hits 200

# Monday morning: weekly report
0 9 * * 1 python -m runtime.safety.evolution.weekly_report
```

## 3. P0 — constitution gate (trust signal)

The gate that intercepts every outbound message. It's been STATIC
(regex secrets, regex PII, optional LLM judge) until P1 produced a
new signal: per-guard precision.

The trust signal layer:

* `compute_guard_trust_score(digest)` — derives a [0.0, 1.0] score
  from the security-class guards' precision. High TP rate (agent keeps
  trying real bad things) → low trust. High FP rate / no hits → high
  trust.
* `classify_trust_score(score)` — buckets into `trusted` / `neutral`
  / `suspect`.
* When `enable_trust_signal=True` and the agent is `suspect`, gate
  upgrades a clean ``allow`` to ``human_gate``. Trust signal NEVER
  relaxes a hard floor (block / rewrite stay regardless).
* Same trust score gates the prompt evolver: `suspect` agents can't
  ship a mutation whose suffix contains relax phrases (`bypass`,
  `skip verification`, etc.).

**Source:** [runtime/safety/constitution/trust_signal.py](../runtime/safety/constitution/trust_signal.py),
[runtime/safety/constitution/gate.py](../runtime/safety/constitution/gate.py)

## 4. P3 — long-task durability

Three layers of "process can die mid-trajectory and we're fine":

### 4.1 Auto-checkpoint (same machine)

Each completed iteration writes a `react_checkpoint` event to the
local journal. SIGKILL / OOM / container restart loses at most N
iterations.

```bash
export ECHO_CHECKPOINT_EVERY_N=5
```

### 4.2 Distributed mirror (cross-machine)

Same payload also pushed to a redis-shape KV. Another worker on
another machine can pull from the mirror to see what tasks need to
be resumed.

```bash
export ECHO_CHECKPOINT_MIRROR_URL=redis://shared-redis:6379/0
```

Mirror has bounded retry (2 attempts × 50 ms) and a circuit breaker
(3 consecutive failures → 30 s cooldown). The local journal is the
source of truth; mirror is best-effort overlay.

### 4.3 Resume CLI

```bash
# List resumable tasks (works against journal AND mirror)
python -m runtime.core.cerebrum.resume_cli list

# Inspect one task
python -m runtime.core.cerebrum.resume_cli show <task_id>

# Actually resume (drives run_react_loop)
python -m runtime.core.cerebrum.resume_cli resume <task_id> \
    --planner-type llm \
    --planner-model claude-haiku-4-5-20251001
```

Each resume writes a `task_resumed` event to the journal tagged
`resume_cli/<source>` for audit.

## 5. Knobs

### Environment variables

| Variable | Purpose |
|---|---|
| `ECHO_DISABLED_GUARDS` | Comma-separated list — temporarily kill guards |
| `ECHO_CHECKPOINT_EVERY_N` | Auto-checkpoint cadence in iterations |
| `ECHO_CHECKPOINT_MIRROR_URL` | Redis URL for distributed mirror |
| `ECHO_ENABLE_TRUST_SIGNAL` | `1` / `0` to override yaml setting |
| `ECHO_DISABLE_GUARD_TELEMETRY` | `1` to disable telemetry recording |

### YAML (`config.local.yaml` > `config.yaml` > `config.example.yaml`)

```yaml
safety:
  # Blanket kill-switch (project baseline)
  disabled_guards:
    - magic-number guard

  # Per-guard fine-grained override (re-enable a single one)
  guard_overrides:
    magic-number guard: false
    weak-test guard: true   # explicit on, even if blanket disabled

  # Trust gate opt-in
  enable_trust_signal: true
```

**Precedence**: kwarg > env > yaml > default. Env-var disabled list
unions with yaml's. Per-guard `guard_overrides: {label: false}` adds
to the disabled set; `{label: true}` removes from it.

## 7. Operational playbook

### "A guard is firing too many false positives this week"

```bash
# Quick fix: kill it for now
export ECHO_DISABLED_GUARDS="magic-number guard"

# Persistent fix: yaml
# edit config.local.yaml:
#   safety:
#     guard_overrides:
#       magic-number guard: false
```

The kill-switch change emits an audit log line + a record to
guard_hits.jsonl tagged `__kill_switch_change__`.

### "A worker died mid-task"

```bash
# Same machine? Check journal
python -m runtime.core.cerebrum.resume_cli list

# Different machine? Check mirror
python -m runtime.core.cerebrum.resume_cli list \
    --mirror-url redis://shared-redis:6379/0

# Continue the task
python -m runtime.core.cerebrum.resume_cli resume <task_id> \
    --planner-type llm
```

### "The agent's trust score dropped this week"

1. Read [logs/weekly_guard_reports/YYYY-WW.md](../logs/weekly_guard_reports/) — look at security-class guards' precision
2. Check whether real bugs are landing (TP) vs noisy detectors (FP)
3. If real bugs: prompt evolver will already be tightening. Review
   the latest variant suffix to confirm it's strict, not loose
4. If noise: file a guard-tuning task to drop the FP rate
